# 기존 운영자 로그인 복구

## 원인과 복구 범위

기준 `962fcaa`의 교인 로그인은 활성 명부에서 이름·정규화된 전화번호가 유일하게 일치하면 `member_auth=roster`, 교인 ID, 세션 버전을 저장하고 `/`로 이동했다. SMS 인증번호는 사용하지 않았고 `/otp/`는 로그인으로 돌려보내는 호환 경로였다. 관리자 화면은 Django 관리자 계정과 기존 TOTP 추가 인증을 사용했다. 사건 의견 작성에는 당시 별도 접속 수단이 필요했다.

`a657c21`에서 교인 로그인 POST를 제거하고 모든 교인 세션에 신규 동의·확인·승인 조건을 적용하면서 기존 운영자도 막혔다. 이번 수정은 이름·전화번호 폼과 기존 세션 생성·제한·CSRF 회전을 복구하되, 서버에 개별 지정된 기존 운영자(`Member.legacy_operator`)만 종전 방식으로 열람·본인 댓글 작성을 허용한다. 신규 신청·일반 교인 승인 정책은 그대로 유지한다. 운영자 권한은 가입 승인이나 본인 확인 완료를 기록하는 필드가 아니다.

모든 계정을 운영자로 바꾸지 않는다. 추가 마이그레이션의 기본값은 False이며 교인 ID나 기존 자료를 변경하지 않는다. URL·폼으로 운영자 여부를 지정할 수 없다. 관리자는 별도 관리자 인증과 MFA를 유지하며 교인 명의로 댓글을 대신 작성할 수 없다. 교인 로그인은 Django 관리자 권한을 부여하지 않는다.

## 운영 반영 순서 — 이 작업에서는 배포하지 않음

1. 실제 운영 서비스의 쓰기를 중지하고 **실제로 마운트된 기존 DATA_DIR**을 확인한다. 실행 환경의 DB·비공개 자료와 설정 파일, 기존 환경변수 설정을 비공개로 백업한다. `python manage.py backup_private <저장소 밖 새 비공개 경로>`를 사용하고 외부 비공개 저장소에 보관한다. 별도의 빈 DATA_DIR에서 `restore_private`와 DB 무결성·ID·자료 검증을 완료한다. 백업에 실제 개인정보가 있으므로 Git에 넣지 않는다.
2. 검토한 코드를 배포할 때 기존 DATA_DIR·볼륨·DJANGO_SECRET_KEY·관리자 계정·ADMIN_MFA_SECRETS·HTTPS·ALLOWED_HOSTS·CSRF_TRUSTED_ORIGINS를 유지한다. 운영에서는 APP_MODE=production을 유지한다. 이 복구에 새 환경변수·공용 비밀번호·고정 인증번호는 필요하지 않다. `seed_demo`를 실행하지 않는다.
3. 서버에서 `python manage.py migrate --noinput`, `python manage.py bootstrap_roles`, `python manage.py collectstatic --noinput`, `python manage.py check`를 실행하고 정상 프로세스로 재시작한다. 기존 시작 스크립트는 해당 초기화 명령을 이미 수행한다. 호스팅·디스크 위치를 변경하지 않는다.
4. 기존 관리자 계정으로 `/admin/login/` 로그인 후 기존 `/admin-mfa/` TOTP를 완료한다. 새 계정을 만들거나 관리자 인증값을 재설정할 필요가 없다. 슈퍼유저 또는 `portal.change_member`와 `portal.manage_legacy_operator` 권한을 가진 관리자만 지정할 수 있다. 새 권한은 기존 명부 관리자 그룹에 자동 부여하지 않는다.
5. `/admin/portal/member/`에서 **실제 기존 운영자 교인 ID**를 확인하고 해당 한 계정의 ‘기존 운영자 로그인 허용 (개별 확인 후 지정)’만 체크한다. 변경 사유를 기록하고 저장한다. 이름·번호를 임의 입력하여 새 교인을 만들지 않는다. 변경은 관리자 이력에 남고 세션 버전이 갱신된다.
6. 관리자와 별도의 브라우저/프로필에서 `/login/`에 그 교인의 기존 이름·전화번호를 입력한다. 로그인은 `/`로 이동해야 한다. E01~E30 상세, 본인 시험 댓글 작성·삭제, 상황판·로드맵을 확인한다. 일반 창에서 관리자 세션과 교인 세션을 혼용해 대필하지 않는다. 운영자 지정은 관리자 계정 로그인과 MFA를 대체하지 않는다.
7. 비로그인·미승인 신규 교인의 직접 상세·댓글·문서 URL 접근 차단을 확인한다. 운영자 권한 철회·비활성화·번호 변경 시 기존 세션도 차단된다. 신규 신청 관련 기존 운영 주체·보유기간·교회 수신 창구가 미설정이면 신규 접수만 계속 차단한다. 이를 운영자 로그인 복구의 필수 환경변수로 요구하지 않는다.

## 이 개발 환경에서 확인한 범위

작업 시작 시 교인 0명·Django 관리자 0명인 개발 DB였다. 따라서 실제 운영자를 임의 지정하지 않았고 운영 계정 접속·실제 영구 디스크·외부 백업 완료를 주장하지 않는다. 수정 전 DB·관련 설정은 `/workspace/private-backups/login-recovery-20261101/`에 저장소 밖 비공개 백업했고 빈 임시 DATA_DIR로 복구했다. 추가 마이그레이션 후 기존 portal 테이블과 auth_user의 원래 컬럼 데이터가 동일함을 확인했다. 실제 운영 반영에서는 위 1~7 단계가 별도로 필요하다.

자동 테스트와 브라우저 검증은 격리 DB의 가상 운영자로 수행한다. 이름·전화번호 로그인 → `/` 이동 → 30개 상세 → 본인 댓글 작성·삭제, 승인 누락 상태에서 운영자만 접근, 다른 교인 사칭 차단, 신규·게스트 차단, 권한 지정·철회와 MFA, 원래 DB 보존을 검사한다. 실제 데이터·인증값을 테스트나 Git에 복사하지 않는다.

## 가상교인 접속 복구 (실제 운영 DB에서 실행 금지)

기존 입력값은 이름 `가상교인`, 전화번호 `01000000000`이며 Django 관리자 계정이 아니다. 개발 모드이고 실제 교인 명부가 없는 전용 개발 DB에서만 다음 명시적 명령을 사용한다.

```sh
APP_MODE=development .venv/bin/python manage.py seed_demo --enable-login
```

기존 가상교인이 있으면 해당 ID·연결·게시글·댓글을 보존하면서 활성 상태와 개발용 운영자 열람 권한만 복구한다. 없으면 synthetic 가상교인 한 명만 생성한다. 반복 실행은 중복 교인이나 승인 기록을 만들지 않는다. 기본 `seed_demo`는 로그인 권한을 부여하지 않으며 시작 스크립트도 자동 실행하지 않는다. 명령은 운영 모드·실제 교인 명부·같은 번호의 충돌 계정이 있으면 변경 없이 거부한다. 로그인과 이미 열린 세션도 운영 모드 또는 실제 교인 명부가 유입된 DB에서는 이 가상 운영자 접근을 차단한다. 일반 이용자 승인 절차와 실제 운영자 권한에는 이 복구를 사용하지 않는다.

명시적 활성화 결과는 현재 개발 DB에만 적용된다. 기존 Cloudtype 운영 DB는 이 환경에서 확인하거나 변경할 수 없다. PR 반영만으로 운영 DB의 가상 계정이 자동 생성·활성화되지는 않는다. 별도의 가상 데이터 전용 개발 인스턴스라면 DB·설정 백업 후 동일 DATA_DIR을 사용하는 콘솔에서 위 명령을 실행하고 교인 로그인으로 확인한다. 실제 교인·개인정보가 있는 서비스에서 이를 실행하거나 접속 제한을 풀어서는 안 된다.
