# 운영·배포 안내

## Cloudtype 배포

Dockerfile 방식으로 이 저장소를 배포하고 8000 포트를 HTTPS 서비스에 연결합니다. 현재 전달받은 Cloudtype Dockerfile 서비스 조회 결과에는 연결된 디스크가 없으며, `/data/portal.sqlite3`는 재배포 후 보존을 보장할 수 없습니다. `DATA_DIR`라는 이름이나 `/data` 경로 자체가 영구 저장을 뜻하지 않습니다. 아래 영구 저장 안내는 실제 지원·마운트·재시작·재배포 검증이 완료된 환경에서만 적용합니다. 해당 환경에서는 UID 10001에 읽기·쓰기 권한을 부여합니다. 임시 컨테이너 디스크에는 운영 데이터를 저장하지 마세요. Django 정적 관리자 파일은 `collectstatic` 후 WhiteNoise로 제공합니다. 정적 파일만 공개하며 `/data/private`는 제외합니다. 한 인스턴스·한 worker만 사용합니다. IP 요청 제한은 직접 연결 주소를 기준으로 하므로 프록시 환경에서 여러 교인의 주소가 합쳐질 수 있습니다. 실제 배포에서 신뢰할 수 있는 프록시의 주소 전달 규칙을 확인하고 요청 제한을 조정하는 검증이 필요합니다. 여러 인스턴스 또는 고동시성이 필요하면 PostgreSQL과 비공개 객체 저장소로 전환하는 별도 작업이 필요합니다.

운영 주체 `OPERATOR_NAME`과 수정·삭제 요청 연락처 `OPERATOR_CONTACT`를 설정하면 개인정보 안내 화면에 표시됩니다. 이 설정과 실제 명부 이용 근거·동의 절차를 운영 전에 확정해야 합니다.

환경변수는 `.env.example`의 이름을 참고하여 Cloudtype 설정에 입력합니다. 앱은 dotenv 파일을 자동 로딩하지 않습니다. `APP_MODE=production`, 충분히 긴 임의 `DJANGO_SECRET_KEY`, 서비스 호스트 `ALLOWED_HOSTS`, HTTPS 주소 `CSRF_TRUSTED_ORIGINS`, 영구 디렉터리 `DATA_DIR`가 필요합니다. `ADMIN_MFA_SECRETS`는 각 관리자 username을 키로 하는 JSON 객체이며 각 값은 개인별 Base32 TOTP 비밀값입니다. 인증 앱과 안전하게 연결하고 다른 관리자에게 동일한 값을 공유하지 마세요. 비밀값은 채팅·Git·로그에 넣지 않습니다.

교인 로그인은 활성 명부의 이름·전화번호 일치로 처리합니다. SMS 업체 연결·발신번호·발송 키·잔액·인증번호 입력은 필요하지 않습니다. 기존 `SMS_API_KEY`, `SMS_API_SECRET`, `SMS_SENDER`는 일반 로그인에서 사용하지 않습니다. 회원가입 없이 기존 교인 UUID로 세션을 만들며 관리자 비밀번호·개인별 TOTP 추가 인증은 유지합니다. 이름·전화번호를 아는 사람의 사칭 위험이 있는 로그인 방식임을 운영 정책에서 안내합니다.

TLS 프록시는 외부에서 들어온 `X-Forwarded-Proto`를 덮어쓰는 신뢰된 프록시여야 합니다. Secure·HttpOnly 세션, CSRF, HTTPS 리다이렉트와 HSTS가 운영 모드에서 적용됩니다. 운영 전 `python manage.py check --deploy`를 실행하세요. `/health/`는 DB·SMS·디스크의 전체 건전성을 보증하지 않는 기본 상태 확인입니다.

## 시연 환경과 자동 가상 교인 생성

시연 환경은 `APP_MODE=development`, 운영 환경은 `APP_MODE=production`입니다. Cloudtype에서 `APP_MODE=development`를 유지하고 이 변경이 포함된 코드로 재배포하면 됩니다. 별도로 터미널에서 `seed_demo`를 실행할 필요가 없습니다. 시작 순서는 마이그레이션 → 개발 모드에서만 `seed_demo` → 역할 초기화 → 정적 파일 수집 → Gunicorn 실행이며 포트는 기존 8000을 유지합니다.

가상 교인은 `가상교인` / `01000000000`, `synthetic=True`로 생성됩니다. 반복 실행해도 중복 생성하지 않고 기존 내부 ID와 게시글 연결을 유지합니다. 실제 명부가 있는 데이터베이스에서는 샘플 생성을 거부하며 개인정보 없는 오류 메시지와 함께 시작을 중단합니다. 이 경우 명부를 삭제하거나 초기화하지 말고 실제 명부용 운영 설정과 별도 시연 데이터베이스를 사용하세요.

로그인 화면은 이름·전화번호 두 항목을 사용합니다. SMS 인증번호를 생성·발송·표시하지 않습니다. 개발·운영 모드에서 같은 명부 일치 로그인을 사용하지만 개발 모드의 샘플 생성과 운영 모드의 HTTPS·Secure 쿠키 차이는 그대로입니다. `APP_MODE`가 없거나 값이 잘못되면 개발 모드로 전환하지 않습니다. 운영 비밀키가 누락되면 시작을 거부합니다.

자동 생성은 기존 데이터의 백업이나 복구 기능이 아닙니다. 임시 디스크에서 데이터가 사라지면 가상 계정은 다시 생성되지만 이전 게시글·자료는 복구되지 않습니다. 운영 전 로그인 DB의 영구 저장·백업 조건을 확인해야 합니다. SMS 연결은 필요하지 않습니다. 이전 데이터 보존과 복원에는 아래의 영구 디스크 및 백업·복구 절차를 사용하세요.

## 관리자와 명부

1. 운영 DB에서 `python manage.py createsuperuser`로 최초 계정을 생성합니다. 공개 회원가입은 없습니다.
2. 개인별 TOTP 설정 후 `/admin/` 로그인, 추가 인증을 완료합니다.
3. 일반 운영 계정은 staff를 지정한 뒤 명부 관리자·내용 편집자·게시 승인자·게시판 관리자 그룹을 개별 부여합니다. 일반 관리자를 superuser로 만들지 마세요. 계정마다 TOTP가 있어야 합니다.
4. `/roster/`에서 XLSX 업로드: `교인명부` 시트, 2행 B열 `이름`, C열 `전화번호`.
5. 검증 결과에서 누락·중복·동명이인·공용 번호·변경 후보·이번 파일에 없는 기존 교인을 확인합니다. 앞자리 0 복구 후보는 자동 반영하지 않습니다. 원본을 확인해 수정된 파일로 재업로드합니다.
6. 같은 교인은 기존 UUID를 유지하고, 변경 후보는 별도 신원 확인 후 기존 ID를 명시적으로 연결합니다. 확정 전 반영하지 않습니다. 동일 이름·번호가 완전히 중복된 행은 건너뛰며 관리자 확인이 필요합니다. 누락 계정을 자동 삭제·비활성화하지 않습니다.
7. 비활성화·연락처 변경은 관리자 화면에서 사유를 기록합니다. 번호·활성 상태 변경 시 기존 세션과 미사용 인증 수단이 무효화됩니다. 게시글의 회원 연결은 유지합니다.
8. 공용 번호는 일반 이름·전화번호 로그인을 차단합니다. `/exception-issue/`에서 관리자가 개인별 신원 확인 사유를 기록한 후 15분·1회 접속 수단을 발급하여 그 개인에게 안전하게 전달합니다. 발급한 코드는 화면에 한 번 표시되며 DB에는 HMAC만 저장합니다. 일반 회원은 다른 공용 번호 계정을 선택할 수 없습니다.

XLSX 원본은 저장하지 않습니다. 검토 데이터는 비공개 DB에 최대 1시간 보관 후 정리합니다. 실명·전화번호를 제공하는 회원 API는 없습니다.

## 사건·헌법·문서

사건에는 발생일, 경과, 사실, 주장, 미확인 사항, 양측 반론, 공식 결정 메타데이터, 운영진 의견을 각각 등록합니다. 초안·검토 중에는 교인에게 공개되지 않습니다. 작성자 외 게시 승인자가 검토하고 승인합니다. 조문은 통합 헌법인지 시행규정인지 표시하고 공식 원문·개정 공고 URL, 개정·시행·확인일, 당시 적용 여부와 관련 이유를 확인합니다. 검증되지 않은 공식 조문 원문은 표시하지 않습니다. 별도 출처와 검토 수준을 표시한 검토 문서의 조항 설명은 읽을 수 있으며 공식 조문과 혼동하지 않게 구분합니다.

원본 PDF는 관리자만 다운로드합니다. 별도로 복구 불가능하게 가린 PDF 열람본을 만들고 텍스트 추출·복사·레이어/첨부·메타데이터 검사를 수행한 뒤 가림 확인을 표시합니다. 앱은 PDF 가림을 자동 수행하거나 복구 불가능성을 보증하지 않습니다. 파일 확장자·크기·PDF 헤더를 검사하고 HTML·실행 파일을 받지 않습니다. 운영 전 외부 문서의 악성 파일 검사 절차도 준비하세요. 문서·원본을 공개 스토리지나 정적 파일 경로에 연결하지 않습니다.

조문·문서 수정은 사건을 검토 중으로 되돌립니다. 사건 작성자와 마지막 내용 편집자는 자신의 자료를 최종 게시 승인하지 못합니다. 문서는 초안으로 업로드하고 별도 승인자가 열람본과 가림 검증을 확인한 뒤 게시 상태로 변경하고, 이어서 사건의 게시를 승인하세요. 게시 승인자는 자료와 사건을 검토한 뒤 게시합니다. 양측에 같은 요청·검토·정정 기준을 적용합니다. 변경 이력은 관리자 전용으로 보존하고 교인에게 수정일을 표시합니다. 회원의 반론·정정 요청과 결과는 본인과 관리자만 봅니다. 공개 정정은 사건 본문에 명확히 반영하고 관리자 사건 양식의 교인 공개 정정·변경 요약에 사유·근거를 기록합니다. 다른 승인자가 게시한 뒤 사건 하단 이력에 표시되며 민감한 원문은 포함하지 않습니다. 원본이나 이전 버전을 자동 공개하지 않습니다.

## 보유기간·백업·복구

운영 주체·실제 문의 연락처·명부 이용의 법적 근거·동의 방식·삭제·보존 기간을 운영 전에 확정하고 정책 화면을 보완하세요. 현재 정책은 초안이며 공개 운영 승인을 대신하지 않습니다. 성향 필드·열람자 추적·찬반 접근 제한은 없습니다.

매일 `python manage.py purge_private`와 `python manage.py clearsessions`를 실행합니다. 삭제 게시글 30일, 처리 요청·변경 이력 90일, 명부 미리보기 1시간, 요청 제한 24시간 기준입니다. 명부 개인정보 삭제는 게시글 보존과 법적 근거를 확인하는 별도 절차로 처리합니다. 관리자에게도 OTP·세션 비밀값 조회 화면이 없습니다.

앱을 중지한 상태에서 비공개 저장소 밖의 새 디렉터리에 백업합니다:

```sh
python manage.py backup_private /secure-backups/new-snapshot
# 다른 빈 영구 디렉터리에서 복구 (서버 중지 필수)
DATA_DIR=/new-data python manage.py restore_private /secure-backups/new-snapshot
python manage.py migrate --noinput
```

백업은 SQLite backup API로 일관된 DB 복사와 비공개 파일·SHA256 manifest를 저장합니다. 파일과 DB 간 일관성을 위해 서버 중지가 필수입니다. 백업은 암호화하지 않으므로 즉시 암호화된 제한 접근 외부 저장소로 이동하고 접근 권한·키 관리·30일 회전 정책을 별도 운영하세요. 복구는 빈 디렉터리에만 가능하고 체크섬·DB 무결성을 확인합니다. 복구 때 이전 세션·OTP는 삭제합니다. 새 배포에서도 동일 영구 볼륨을 마운트합니다. 실제 Cloudtype 재배포·디스크 복구는 배포 계정에서 별도 검증해야 합니다.

운영 모드 보안 검사에는 HSTS 하위 도메인 적용(W005)·브라우저 preload(W021) 권고 경고가 남습니다. 이 사이트가 소유하지 않거나 HTTPS가 보장되지 않는 다른 하위 도메인까지 정책을 확대하지 않기 위해 기본값을 유지했습니다. 실제 도메인 관리자가 전체 하위 도메인의 HTTPS를 확인한 뒤 별도로 검토하세요.

## 사건 자료와 내부 메모

[사건 HTML 본문 안내](CASE_REVIEW.md)에 인증된 서버 템플릿 표시·발췌 수정 절차를 정리했습니다. 이번 본문은 사건 DB 등록이나 별도 파일 배치를 요구하지 않습니다. 실제 HTML 본문이 포함된 코드는 저장소 비공개 확인 후 PR·머지·사용자 배포로 반영합니다. 기존 관리자 사건 자료 관리 기능과 데이터는 삭제하지 않습니다. 활성 명부의 이름·전화번호 로그인 후 본문이 표시되며 관리자 추가 인증·HTTPS·로그인 DB 보존 설정은 별도로 확인해야 합니다.


## 사건별 의견·한 단계 답글

사건 본문은 기존 HTML 템플릿 E01~E30 그대로이며 `Case` 행이나 JSON 등록이 필요 없습니다. 제목과 참여 안내만 정리하고 네 영역 뒤에 실명 의견을 연결합니다. `portal/reading_registry.py`가 유효한 사건번호의 단일 목록입니다. 새 `CaseComment`와 `Post.reading_key`, `Request.reading_key/comment`는 기존 사건 외래키·ID를 변경하지 않습니다.

일반 명부 로그인은 열람용이며 개인 신원 확인 완료가 아닙니다. 의견 작성·수정·삭제는 기존 `/exception-issue/`에서 명부 관리자가 추가 인증 후 별도 신원 확인 사유와 확인 표시를 남기고 발급한 개인별 일회용 접속 수단을 `/exception/`에서 사용해야 합니다. 발급 수단은 15분·1회 한정이고 확인 세션은 최대 1시간입니다. 과거 명부 로그인 세션이나 과거 예외 세션을 자동 승격하지 않습니다. 번호 변경·비활성화·로그아웃으로 세션이 무효화됩니다. 개발 모드에서는 기존 정책대로 가상 교인에만 이 수단을 발급합니다. 관리자 열람 계정만으로는 교인 의견을 쓸 수 없습니다. SMS 등 새 외부 서비스 설정은 없습니다.

의견과 답글은 한 단계만 지원하며 서버에서 작성 교인·등록 실명·비민감 구분 표기를 결정합니다. 수정 전 내용은 관리자 전용 `Revision`에 남기고 작성자는 자기 글만 수정·삭제할 수 있습니다. 삭제된 자리와 답글 연결은 유지합니다. 게시판 관리자는 관리자 추가 인증 후 의견 본문을 고쳐 쓰지 않고 숨김 상태·공개 분류·비공개 근거만 변경합니다. `bootstrap_roles`를 실행하면 기존 게시판 관리자 역할에 의견 조회·조치 권한이 추가됩니다. 개인정보, 욕설·위협, 도배, 무관한 인신공격에 같은 기준을 적용하고 비판의 방향은 사유로 삼지 않습니다.

의견의 신고·정정·비공개 반론 제출 링크는 사건번호와 댓글을 미리 연결합니다. 접수 원문과 관리자 답변은 본인과 권한 있는 관리자만 봅니다. 실제 접수 반론을 공개하려면 요청의 유형·연결 사건·실제 접수 내용을 확인하고 `공개용 발췌`에 불필요한 개인정보를 제거한 내용을 작성한 뒤 검토 확인으로 `반론 공개 승인`을 선택합니다. 일반 댓글과 구분해 해당 사건 네 번째 영역에 표시됩니다. 이 확인은 법적 판단이나 원자료 검증 승격이 아닙니다. 관리자 답변이나 비공개 접수 원문을 자동 공개하지 않습니다.

배포 전 기존 SQLite와 비공개 파일을 `backup_private`로 백업하고 컨테이너 밖의 제한 접근 저장소로 실제 반출·체크섬 확인을 마쳐야 합니다. 컨테이너 내부 사본만으로 외부 백업 완료라고 판단하지 마세요. `python scripts/verify_backup.py`는 가상 교인·게시글·댓글·답글·요청·이력의 로컬 복구와 ID 연결, 무결성, 기존 세션 무효화를 검증합니다. 실제 운영 백업을 대신하지 않습니다.

검토·머지·배포는 사용자가 별도로 수행합니다. 백업 확보 및 운영 저장 방식 확인 후 기존 시작 스크립트의 `migrate --noinput`이 추가 마이그레이션 `0010_member_discussions`를 적용합니다. 사건 등록 명령, DB 초기화, 포트 변경은 필요 없습니다. 운영에서 영구 저장이 확인되지 않았다면 재배포로 명부·게시글·댓글이 사라질 위험이 남습니다. 이 PR은 저장소나 외부 DB를 새로 만들지 않으며 Cloudtype 보존 문제를 해결했다고 주장하지 않습니다.

보유기간 정리 시 삭제 의견 본문·작성자 표기는 30일 후 제거하고 수정·관리자 이력은 90일 기준으로 정리합니다. `purge_private`를 기존 일일 작업에 포함하세요. 로컬 동일 디렉터리 재시작 테스트는 실제 Cloudtype 영구 디스크·재배포 보존 검증과 구별합니다.
