# 교인 전용 암호화 사건 본문 배포

## 본문 공급과 열람

사건 페이지 `/`는 서버 배포 파일 `server_materials/case-reading.enc`를 메모리에서 복호화하여 읽습니다. 사건·조문·결정·문서 DB나 MEDIA_ROOT의 평문 파일은 사용하지 않습니다. 검색 UI/처리는 없으며 최초 진입에 전체 본문을 표시합니다. 사건마다 **발생 날짜 → 사건 경과 → 관련 교단 헌법·규정 → 쟁점과 추가 확인사항**을 PC·모바일 모두 세로로 표시합니다. 접기·탭·말줄임·내부 스크롤·페이지 분할은 없습니다.

자료 번호는 열람용 식별자이며 공식 재판 사건번호가 아닙니다. 일·월·연도·기간의 날짜 표현을 보존하고 선후관계를 확정할 수 없는 사건은 이유와 함께 별도 구분합니다. 출처와 원문 발췌·역할명 치환 발췌·편집자 요약, 주장·검토 의견·미확인 사항을 구분합니다. 검토 문서의 규정 설명은 공식 원문 미대조로 표시하며 판본·개정·시행·사건 당시 적용과 이후 진행을 추정하지 않습니다. 무죄·불기소·판단 제외·확정은 서로 다릅니다. 내부 전략과 불필요한 개인정보를 옮기지 않습니다.

기존 `/cases/material/<자료번호>/`는 동일 사건 앵커로 이동합니다. 숫자 `/cases/<ID>/`는 본문에 대조한 별칭만 연결하며 운영 ID가 로컬 ID와 같다고 가정하지 않습니다. 확인되지 않은 번호는 404입니다. 기존 DB·게시글·문서 ID와 연결, DB 관리자 기능·미리보기·자료 등록·반론 접수는 보존하지만 DB를 편집해도 암호화 본문은 자동으로 바뀌지 않습니다.

## 인증·암호화·파일 경계

기존 활성 교인 세션 또는 활성 관리자(직원·portal.view_case·유효한 추가 인증)가 확인된 뒤에만 복호화합니다. 일반 교인 로그인·명부·관리자 추가 인증을 완화하지 않습니다. 실제 본문은 APP_MODE=production에서만 읽으며 개발 OTP로는 읽을 수 없습니다. 텍스트는 Django 자동 이스케이프를 사용하고 응답에 no-store/private 및 Vary: Cookie를 적용합니다. 공개 로그인/정책/오류 응답이나 별도 API로 본문을 보내지 않습니다.

Python 표준 라이브러리는 인증된 암호화 API를 제공하지 않으므로 검증된 cryptography 라이브러리를 사용합니다. 임의 AES-256 키와 12바이트 임의 nonce로 gzip 본문을 AES-GCM 암호화하고, AES 키는 수신자의 RSA 공개키로 RSA-OAEP(SHA-256/MGF1-SHA-256) 암호화합니다. 고정 형식 식별자를 추가 인증 데이터와 OAEP label에 묶습니다. 자체 암호 알고리즘을 구현하지 않습니다. gzip과 Base64는 압축/표현이며 암호화가 아닙니다. 키 길이는 RSA 3072~8192비트입니다. 암호문 인증 후에만 제한 크기로 압축을 해제하고 구조를 검사합니다.

평문은 메모리에서만 사용하며 /data·MEDIA_ROOT·임시 파일에 쓰지 않습니다. 프로세스 메모리와 런타임 비밀키에 접근 가능한 운영자는 본문을 읽을 수 있습니다. 암호문도 Django 정적 폴더나 URL에 노출하지 않습니다. 다만 저장소가 공개이면 커밋한 암호문 자체는 GitHub에서 볼 수 있습니다. 이는 평문 공개와 다르며 사용자 승인 범위의 암호문만 배포합니다. 개인키·원문·편집 JSON·평문 본문·DB·명부·토큰은 Git·Docker 빌드 입력·PR·로그에 포함하지 않습니다.

## 키 생성과 한 번의 비밀 환경변수 설정

사용자 Mac에서 RSA 개인키를 생성·보관하고 **공개키만** 편집 작업자에게 전달합니다. 개인키를 채팅·PR·로그로 보내지 않습니다. 아래는 Mac 기본 OpenSSL을 사용하는 새 전용 키의 생성 예입니다. 이미 생성한 키가 있으면 재생성하지 말고 그 키를 사용합니다.

```sh
umask 077
shinsung_key_dir="$(mktemp -d "$HOME/Downloads/shinsung-key.XXXXXX")"
openssl genrsa -out "$shinsung_key_dir/private.pem" 3072
openssl pkcs8 -topk8 -nocrypt -in "$shinsung_key_dir/private.pem" \
  -outform DER -out "$shinsung_key_dir/private.der"
# 전달해도 되는 공개키 한 줄. 개인키를 출력하지 않습니다.
openssl rsa -in "$shinsung_key_dir/private.pem" -pubout -outform DER 2>/dev/null |
  openssl base64 -A
```

검토된 실제 본문을 이 공개키로 암호화한 파일이 PR에 포함되어야 배포 준비가 완료됩니다. 사용자에게 긴 Base64 본문이나 컨테이너 파일 수동 복원을 요구하지 않습니다. 개인키의 **PKCS#8 DER를 Base64로 표현한 단일 문자열**을 Cloudtype 런타임 **비밀 환경변수 CASE_READING_PRIVATE_KEY**에 한 번 설정합니다. PEM 헤더나 본문 파일을 넣는 변수가 아닙니다. Mac에서 화면·명령 기록에 키 값을 출력하지 않고 클립보드로 복사할 수 있습니다.

```sh
openssl base64 -A -in "$shinsung_key_dir/private.der" | pbcopy
```

Cloudtype의 비밀 변수 입력에 붙여 넣고 개인키는 별도로 제한 접근·암호화된 백업에 보관합니다. 환경변수를 Dockerfile, 빌드 인자, Git 파일, 일반 로그에 넣지 않습니다. 키를 잃어버리면 해당 암호문을 복호화할 수 없습니다. 같은 공개키로 후속 본문을 암호화하면 비밀 변수는 재설정할 필요가 없습니다. 키 교체는 새 암호문과 해당 비밀 변수의 배포를 함께 검토합니다.

## 편집·검토·머지·배포

원문 source.docx와 기존 initial.review.json을 대조한 별도 평문 case-reading.body는 체크아웃 밖에서 편집합니다. 전략·개인정보 제외, 출처·날짜·표현 분류·자료 번호·별칭을 재검토하고, 내용 변경은 비공개로 검토한 뒤 암호문과 코드 PR을 함께 승인·머지·배포합니다. 평문 검토를 암호문 Git diff로 대신할 수 없습니다.

공개키 DER 파일을 전달받은 작업자는 다음 도구로 암호문만 만듭니다. 입력 파일은 비공개 경로이며, 개인키는 필요하지 않습니다. 출력 파일이 이미 있으면 도구는 덮어쓰지 않습니다. 새 버전 파일로 생성·검토한 후 배포 암호문을 교체합니다.

```sh
.venv/bin/python scripts/encrypt_case_reading.py \
  --source /private-review/case-reading.body \
  --public-key-file /private-review/recipient-public.der \
  --output server_materials/case-reading.enc
```

앱의 Dockerfile COPY로 암호문이 코드와 함께 이미지에 포함되므로 컨테이너 재생성/재배포에도 동일 본문을 제공합니다. 복호화 키는 런타임 비밀 변수로 계속 공급해야 합니다. 평문 /data 파일·DB 등록·seed_demo·영구 본문 볼륨은 필요하지 않습니다. 기존 수동 평문 파일이 있어도 로더는 사용하지 않습니다. Cloudtype의 Dockerfile 서비스에 영구 디스크가 있다는 가정은 하지 않습니다.

운영 담당자의 최소 순서:

1. 기존 인증 DB와 비공개 자료의 보존/백업 방법을 먼저 확인합니다. 기존 DATA_DIR·DB·명부·게시글을 삭제·초기화·임의 이전하지 않습니다.
2. 해당 암호문의 수신 개인키를 CASE_READING_PRIVATE_KEY 비밀 변수로 설정하고 기존 APP_MODE=production, HTTPS·실제 SMS·관리자 추가 인증 설정을 확인합니다. 개인키는 빌드에 넣지 않습니다.
3. 검토한 PR을 사용자가 머지하고 Cloudtype에서 해당 코드를 배포합니다. 작업자는 자동 머지/운영 배포를 하지 않습니다.
4. 실제 서비스에서 다음 안전한 진단을 실행합니다. 본문·키·개인정보는 출력하지 않으며 실패하면 종료 코드 1입니다.

```sh
python manage.py case_reading_status
```

정상 출력은 ready=true와 사건/날짜순/불확실 묶음 수량입니다. 실패 이유는 ciphertext_missing(배포 파일 누락), ciphertext_invalid(형식/읽기 오류), private_key_missing(비밀 변수 누락), private_key_invalid(잘못된 인코딩/키 형식), decrypt_failed(키 불일치 또는 인증 실패), body_invalid(압축/본문 구조 오류), development_forbidden(운영 모드 아님) 중 하나입니다. 오류의 원문·키·예외 상세는 출력하지 않습니다. 웹 페이지는 일반 안내와 503/시연 차단만 반환합니다.

5. 실제 교인 SMS 인증 또는 권한·추가 인증을 갖춘 관리자로 전체 본문·네 영역·출처·날짜·직접 링크를 확인합니다. 로그아웃/비활성 접근, 정적 파일/별도 주소 노출 차단, 캐시 방지를 확인합니다. 재시작 및 재배포 후 진단과 본문을 다시 확인합니다.

## 별도로 남는 인증 DB 보존 문제

현재 인증 DB는 SQLite DATA_DIR/portal.sqlite3입니다. Dockerfile의 기본 DATA_DIR=/data는 컨테이너 내부 경로일 뿐 영구 볼륨의 증거가 아닙니다. 본문 암호문을 이미지에 포함해도 교인 명부·관리자·세션·게시글·문서 DB가 재배포 후 유지되는 것은 아닙니다. 영구 디스크 미지원 환경의 인증 DB 보존은 미해결이며 실제 운영 저장 구조·백업·복구/이전 방식을 별도로 결정·검증해야 합니다. 새 유료 DB/스토리지 가입이나 인증 DB 이전은 이번 본문 변경에서 수행하지 않습니다. 기존 startup 마이그레이션·역할 초기화·정적 수집·포트 8000·Gunicorn 구조를 유지합니다.

로컬 검증용 세션/가상 테스트와 실제 운영 SMS·Cloudtype 화면·DB 보존은 구분하여 보고합니다. PR 머지·진단 성공·로컬 테스트만으로 운영 인증과 재배포 후 인증 DB 보존이 검증되었다고 보고하지 않습니다.
