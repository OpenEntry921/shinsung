## 남은 확인

원문 MD만 확보했고 PDF27개·회신 이미지1개는 이번에 받지 않았습니다. MD가 설명하는 직접 대조를 이 구현이 수행한 검증으로 승격하지 않습니다. 자료 목록 28개는 모두 미연결입니다. 이름·쪽수는 표시하지만 가짜 URL이나 빈 다운로드 버튼은 만들지 않습니다.

원자료를 이미 등록했다면 `timeline_links.py`의 `SOURCE_DOCUMENT_IDS`에 정확히 검토한 자료 코드와 기존 Document ID를 연결합니다. 번호 순번이나 제목의 유사성으로 자동 대응하지 않습니다. 동일 ID를 서로 다른 자료 코드에 중복 배정하면 연결을 숨깁니다. 기존 원본 파일·저장소는 복사하지 않고 기존 인증된 reading 경로만 사용합니다. 게시·가림·관련 기존 사건의 게시·실제 열람 파일 존재가 확인되지 않으면 연결하지 않습니다. 본문은 링크가 없어도 표시합니다.

MD에 포함된 날짜·판본 확인 항목 13개를 별도 비공개 검토 기록에 그대로 남겼습니다. 기간이 겹치는 배열도 원문 순서를 유지합니다. 기존/새 정리의 날짜·작성·접수·송달 표현 차이는 자동 보정하지 않습니다. 상고 접수/결과·확정 효력, 변경 허가, 회신·환급, 경찰 접수·수사·처분 등 미확인 후속 상태는 원문 그대로 남습니다. 양측 주장을 새로 판정하지 않습니다.

## 공개 범위 확인과 제출 이력

최초 구현 당시 GitHub 웹 메타데이터의 `repository_public=true`를 확인하여 실제 본문 HTML을 `.git/info/exclude`로 보호하고 커밋·푸시를 보류했습니다. 2026-11-03 사용자가 Private 전환과 PR 생성을 요청했습니다. 비인증 웹 접근은 404로 바뀌었고 기존 Git 연결에서는 저장소 접근을 확인했습니다. GitHub API 조회는 이 작업 환경에서 차단돼 있습니다. 이후 커밋·원격 업로드·PR의 실제 성공 여부는 최종 작업 보고를 따릅니다. 다른 코드만 먼저 올려 불완전한 빌드를 배포하지 마세요. 최초 구현 단계에서는 로컬 변경과 비추적 본문을 함께 보존했고, 사용자 Private 전환 요청 후 실제 본문을 제출에 포함했습니다.

원문 MD·비공개 PDF·회원 DB·명부·비밀값은 커밋하지 않습니다. **저장소를 Private으로 전환하고 확인한 뒤** 실제 본문 템플릿과 이번 변경 전체를 검토하여 사용자 본인이 커밋·푸시할 수 있습니다. 공개 여부를 확인하지 않은 상태에서 ignore를 강제로 해제하지 마세요. 사이트 로그인 제한은 GitHub 소스 공개를 막지 못합니다.

기준 커밋은 위 ca4fc38입니다. 최초 구현은 로컬 미커밋 상태로 보존했고 이후 사용자의 별도 요청에 따라 이번 타임라인 변경만 제출합니다. 기존 보류 SMS 작업은 포함하지 않습니다. 실제 커밋·푸시·PR 상태는 최종 보고에서 구분하며 머지·배포는 수행하지 않습니다. 작업 디렉터리는 Mac의 별도 clone으로 자동 복사되지 않습니다.

## 사용자 수동 PR·머지·운영 반영 순서

1. 저장소를 Private으로 전환·확인합니다. 기존 운영 DB의 외부 백업과 복구 가능성을 별도 확인합니다.
2. 이 로컬 작업 디렉터리에서 diff와 새 파일을 검토합니다. 제외된 실제 본문 파일이 존재하고 70개인지 확인하고, 비공개 확인 후 해당 파일까지 포함해 이번 작업만 커밋합니다. 원문 MD와 비공개 검토·캡처는 제외합니다.
비공개 전환을 확인한 뒤에만, 실제 본문 파일의 로컬 제외 규칙을 검토하고 명시적으로 추가할 수 있습니다. 아래 명령은 이 작업에서 실행하지 않았습니다.

```sh
# Private 상태를 확인한 뒤에만 실행
 git add -f portal/templates/portal/integrated_case_reading.html
```

다른 변경 파일도 이번 작업분만 선택해 추가하고 커밋한 뒤 다음 단계로 진행합니다.

3. 사용자가 직접 작업 브랜치를 푸시합니다. 자동 푸시·강제 푸시·main 직접 푸시는 하지 않습니다.

```sh
git push -u origin feat/integrated-case-timeline
```

4. 원격 업로드가 실제 성공한 뒤 GitHub에서 base `main`, compare `feat/integrated-case-timeline`을 선택해 사용자가 직접 PR을 만듭니다. 현재 원격에 브랜치가 있다고 가정하지 마세요.
5. GitHub Actions `Portal validation`과 실제 70개 본문·순서·출처·기존 연결 보존을 검토합니다. 개인정보 포함 여부와 저장소 공개 범위를 다시 확인합니다. 다른 보류 작업의 커밋·마이그레이션이 섞이지 않았는지 확인합니다.
6. 사용자가 검토 결과를 확인한 뒤 직접 머지합니다. 저장소에서 확인된 workflow는 테스트뿐이며 Cloudtype 자체 자동 배포 연결은 이 환경에서 확인하지 못했습니다. main 머지가 서비스의 자동 배포를 촉발하도록 설정됐는지 운영 화면에서 먼저 확인해야 합니다.
7. 실제 본문 파일을 포함한 코드가 배포되면 별도 사건 가져오기/시드 명령은 필요 없습니다. 기존 시작 스크립트의 `migrate --noinput`이 새 사건번호 제약을 적용합니다. 인증 DB·파일은 기존 설정 그대로 보존해야 합니다. 이 작업에서 실제 운영 마이그레이션·서비스 재시작은 실행하지 않았습니다.
8. 배포 후 정상 운영 인증으로 T01/T35/T70과 기존 E01/E30, 새/기존 댓글·문서 권한을 확인합니다. 실제 운영 확인은 미실행입니다.

되돌리기: 운영 DB와 파일의 일관된 외부 백업·체크섬 확인은 기존 `backup_private`/`restore_private` 절차를 따릅니다. 단순 표시를 되돌릴 때 이미 생성된 T번호 의견을 삭제하거나 E번호로 옮기지 않습니다. 새 번호 데이터가 있다면 이전 E전용 DB 제약으로 무조건 역마이그레이션하지 마세요. 기존 코드를 되돌리더라도 확장된 DB 제약과 데이터를 보존하고 새 기록을 다시 열람할 수 있게 유지하는 복구 계획을 먼저 검토합니다. 백업 이후 작성 내용을 잃을 수 있는 무조건 복원도 하지 않습니다.
